**2026-08-07 — Migrations get the SQL that undoes them, from 0041 on (#365):** preparing the runbook for the two pending prod migrations turned up a standing gap: **0 of 42 migrations had a `down.sql`**, while the global standard says "Database migrations are reversible. Always include a down() migration." Prisma Migrate has no built-in down, so the convention here is a sibling `down.sql` applied with `prisma db execute` — and nothing enforced it. ⚠️ **The other 40 are deliberately not back-filled.** Several are irreversible in principle (data backfills that discard the prior value; enum additions Postgres cannot undo), and a `down.sql` that reads as authoritative but is wrong is *more* dangerous than its absence — it invites someone mid-incident to run destructive SQL with confidence. The honest position is "from 0041 the convention holds; below it, read the migration and decide", and the cutoff is a single constant (`REVERSIBLE_FROM = 41`) rather than a 40-entry grandfather list that would need editing forever and would silently stop covering whatever was added below it. **0041's down is partial by nature and says so in the file**: Postgres cannot remove a value from an enum type, so `WEBHOOK_GENERIC` stays present-but-unused (inert — nothing reads it unless a row carries it). Its real substance is a guard that REFUSES the rollback if any WEBHOOK_GENERIC channel exists, because dropping `signingSecret` under live rows does not fail at rollback time — it fails later at send time, when the dispatcher reaches for a signing key that is gone, and a rollback that converts an obvious error now into an obscure one next Tuesday is worse than one that refuses. **0042's down is symmetric in schema but not in data**: `DROP TABLE` takes the indexes, four foreign keys and the RLS policy with it, but every row is an operator's judgement about a split cheque or a transposition, none of it derivable from the ledger — so the file carries the `CREATE TABLE ... AS SELECT` backup statement above the drop. A third assertion requires each `down.sql` to carry real prose, because a bare `DROP TABLE x;` is exactly the failure this convention exists to prevent: it reads as symmetric when it is not. **Both downs were then EXERCISED end to end**, on a disposable Neon branch forked from dev (`br-falling-queen-ak8e5udm`, deleted afterwards) rather than reasoned about — the shared dev database was never touched, and Chris authorised the fork/exercise/delete explicitly. 0042's `DROP TABLE` took the table, its 4 indexes, all 5 foreign keys and the RLS policy with it, and left `reconciliation` / `bank_transaction` / `gl_entry_line` / `app_user` intact: no cascade damage. 0041's guard did the thing it exists for — with a real WEBHOOK_GENERIC channel inserted it **REFUSED** (`Refusing to roll back 0041: 1 WEBHOOK_GENERIC channel(s) still exist`), and with none it passed through and dropped the column cleanly. **The enum value survived the rollback**, which is the irreversible part the file documents — now confirmed empirically instead of asserted. Re-applying both forward migrations restored the original schema exactly: column back, table back, 4 indexes, 5 FKs, 1 policy, RLS enabled. So the round trip down→up is proven, not assumed. No migration.

**2026-08-05 — The entry-number race was real, and reproduced on the first try (#344):** top of the logged-not-fixed list from #337. `entryNumber` is allocated as `count() + 1` inside the write transaction, which is not atomic — two posters that read the count before either commits compute the same next number, and the loser hits `@@unique([tenantId, entryNumber])` and is told its entry failed. Jitter is what actually breaks the tie, with backoff only to stop a large herd spinning. Deliberately NOT retried when the caller passes its own transaction: the failed statement has already poisoned it, so retrying inside would fail differently and hide the cause — the collision propagates and the transaction's owner retries it whole. `tests/entry-number-concurrency.test.ts` asserts the PROPERTY (every post lands; numbering is distinct, gap-free 1..12; the ledger agrees with what callers were told) rather than a timing outcome, and was run 5× consecutively to check it isn't flaky before shipping — a probabilistic fix proven once is not proven. **2026-08-04 — Reconciliation transaction matching (the last NetSuite-parity matrix item):** a reconciliation used to compare two NUMBERS — the GL balance against a supporting balance (typed, or auto-pulled from a sub-ledger) — so when they disagreed the operator learned the SIZE of the difference and nothing about its shape. EXCLUDED feed lines are not reconciling items — they were triaged as "not ours". **2026-07-18 — Inventory booking engine (Beancount adoption, slice ④ / part 1 of the lots arc):** the pure algorithmic core of lots & cost basis (`src/lib/accounting/inventory.ts`). `bookReduction(held, reduceUnits, method, opts)` decides which lots a sale draws down and computes cost relieved + realized gain (proceeds − cost basis, driven by basis not price). **2026-07-18 — Balance assertions (Beancount adoption, slice ①):** first slice from `docs/spec/beancount-adoption-study.md` (#295). New `BalanceAssertion` table (migration 0027, additive: table + `AssertionStatus` enum + FKs, no backfill, not mirror DDL) records "this account held exactly this much on this date", and `checkBalanceAssertions()` (`src/lib/accounting/balance-assertions.ts`) verifies them. Where `postJournalEntry` enforces correctness at the moment of WRITE, this enforces it ACROSS TIME — catching drift no single write would reject (double-posted import, missed reversal, mapper regression) on the date it first appears. **Complementary to `Reconciliation`, not a replacement**: reconciliation is the periodic human attested control; this is the cheap machine tripwire. Reuses `getTrialBalance` rather than inventing a second notion of "the balance" (one TB per distinct asOf date, so N assertions on a date cost one query); default tolerance derived from `Currency.decimals` (USD→0.01, JPY→1); `expectedAmount` on the account's normal side. ⚠️ **asOf is END-of-day** (`documentDate <= asOf`, matching getTrialBalance) — Beancount asserts at the START of the date; the divergence is deliberate and documented in schema + module + tests, because mixing the two silently answers a different question. **v1 is ADVISORY** — reports only, does not gate posting or close (that's a separate decision). Tests cover exact-PASS, real-FAIL, explicit-tolerance override, currency-derived default tolerance, the end-of-day convention, tenant isolation, and the persist cache. **Deploy note:** migration 0027 needs `prisma db push` on personal-books + any prod.
**2026-07-18 — Account commodity constraint + dated lifecycle (Beancount adoption, slice ②):** second Tier-1 item from `docs/spec/beancount-adoption-study.md` (#295). `Account` gains `allowedCurrencies String[]`, `openedOn` and `closedOn` (migration 0028, additive columns, no backfill), and **`postJournalEntry` enforces both** — so every caller (UI, importers, cron, sub-ledgers) inherits them from the single write path. Closes two real holes: nothing previously stopped a EUR posting landing in a USD-only cash account, and `active: Boolean` **cannot answer "was this account valid on the ENTRY's date"**, which is the only question that matters for a backdated post. New errors `AccountCurrencyNotAllowedError` / `AccountNotOpenError` mirror `AccountBookScopeError`. **Boundaries are INCLUSIVE** — postable on `[openedOn, closedOn]`. ⭐ **INERT BY DEFAULT, which is what makes it safe on a populated ledger:** `allowedCurrencies` defaults to `[]` (unconstrained) and both dates to NULL (unbounded), so no existing account changes behaviour until someone opts in — the full suite staying green is the proof. Tests lead with that regression guard, then cover allowed/refused currency and all four date boundaries (before-open, ON-open, ON-close, after-close). **Deploy note:** migration 0028 needs `prisma db push` on personal-books + any prod.
**2026-07-18 — Commodity + price database (Beancount adoption, slice ③; Chris greenlit the Layer-2 extension):** Tier-2 item ③ from `docs/spec/beancount-adoption-study.md` (#295). New `Commodity` (tenant master data — symbol/name/assetClass, unique per `(tenant, symbol)`, like Item/Party) + `CommodityPrice` (value of one commodity unit in a currency on a date) tables (migration 0029, additive). `FxRate` is currency→currency and Currency is ISO-4217-keyed by design, so a security price was previously **unrepresentable**; this is the seam for mark-to-market / holdings valuation / per-commodity balance assertions. **ADDITIVE Layer-2 extension** — Currency, FxRate and the posting path are untouched. `getCommodityPrice()` (`src/lib/accounting/commodity-price.ts`) resolves **on-or-before** (same convention as `resolveFxRate`); `recordCommodityPrice()` upserts with **last-write-wins** per `(commodity, currency, date)` (matching Beancount's "last price declaration on a day is retained"). Tenant-scoped throughout; `null` for "no price" is a normal answer, never a throw. Tests: exact/between/on/after resolution, before-any→null, unknown-commodity→null, currency-specificity→null, upsert last-wins (one row), tenant isolation. **Deploy note:** migration 0029 needs `prisma db push` on personal-books + any prod. **2026-07-18 — `pad` for balance assertions (Beancount adoption, slice ① part 2):** `padBalanceAssertionAction` (`src/app/actions/pad-balance-assertion.ts`) posts the adjusting entry that makes an unmet assertion true — the **opening-balances** path: assert what an account held on day one, pad it against equity, and the ledger carries a real audited entry instead of a hand-keyed plug. **Deliberate divergence from Beancount, where `pad` inserts silently:** here it is explicit, human-triggered, audited, and flows through `postJournalEntry` (CLAUDE.md #2/#3) — nothing auto-pads. Direction is DERIVED from `delta` + the account's `normalBalance` (short DEBIT-normal → Dr account / Cr pad; short CREDIT-normal → Cr account / Dr pad), never supplied. Observed balance is recomputed at pad time via `getTrialBalance` — never padded from the cached result. **Idempotency is enforced by the DATABASE, not a status flag:** the entry carries lineage `(SUBSTRATE, BalanceAssertion.pad, <assertionId>)` and the existing `gl_entry_header_lineage_uniq` partial unique index turns a second pad into P2002 → "already been padded". **NO schema change** (no migration, fingerprint unchanged) — the lineage triple does the work. Shares one definition of "satisfied" with the checker via exported `resolveTolerance`/`evaluateAssertion`. Tests cover both normal-balance directions, already-satisfied refusal, same-account refusal, tenant isolation, the audit row, and the real P2002 path (disturb the balance after padding, then retry).


**2026-07-18 — Lot persistence (Beancount adoption, slice ④ / part 2 of the lots arc):** the storage layer under the pure booking engine (part 1). **2026-07-18 — Commodity trade posting (Beancount adoption, slice ④ / part 3 of the lots arc):** the integration between the ledger and lots. `src/lib/accounting/commodity-trade.ts`: `recordCommodityPurchase` (post Dr Investment / Cr Cash AND `augmentLot`, atomic) + `recordCommoditySale` (`getOpenLots` → `bookReduction` → post the disposal JE → `consumeLots`, atomic). ### BlackLine arc decisions (2026-06-08 → 2026-06-09)

- **Frozen-snapshot pattern, applied uniformly** — `Reconciliation.glBalance` + `Reconciliation.tolerance`, `FluxLine.priorAmount` + `FluxLine.currentAmount` are captured at sign-off / generation time, not computed on read. Reason: backdated JEs into a signed period would otherwise retroactively flip a RECONCILED recon into EXCEPTION (and vice versa). The auditor's principle "what did the preparer see when they signed" rules. Trade-off: snapshot can drift from real-time GL if the period reopens; this is accepted because period close enforces a hard boundary.
- **3-level cascade resolver for recon defaults** — `Account.reconTolerance` → `ReconciliationConfig.defaultTolerance` → BlackLine baseline ($0). Same pattern for `requiresReview` and `category`. Reason: a controller can set a per-tenant default once, override on the few accounts that need different treatment, and never re-litigate the question. Reads cleanly, audits cleanly.
- **Strict segregation of duties at the Server Action layer** — `preparer.id !== reviewer.id` enforced via `SAME_USER` error code rather than RLS. Reason: the rule is logical, not row-level; the same user IS the actor for both actions across time. Server Action is where the policy lives.
- **DFS cycle prevention on close-task dependencies** — `CloseTask.dependsOnIds` is enforced via depth-first walk in the Server Action, NOT a Prisma constraint. Reason: Prisma can't validate DAG-ness at the schema level. Walk happens before insert; cycle → SoftError → 400. Wall-clock cost is negligible at the task scale (50–200 tasks per period).
- **Audit log: ONE aggregate row on bulk operations, ONE per-line on commentary** — bulk waive of 30 flux lines writes a single `audit_log` row with `metadata.count = 30`; per-line commentary writes one row each (different commentary text is the audit evidence). Reason: noisy bulk rows make `audit_log` unreadable; per-line is fine when each carries unique evidence.
- **Period-close gate composes Phase 1 + Phase 2 + Phase 3** — `checkPeriodClosePrerequisites(periodId)` returns the list of (recon not RECONCILED, required task not DONE, flux statement not FINALIZED) blocking signoff. UI shows the list; admin override is still possible (with `bypass` audit log entry). Reason: the three pillars are conceptually independent but operationally must all close together — the controller wants ONE gate to consult.
- **`audit_log` append-only DB constraint blocks tenant cleanup in tests** — `prisma.tenant.deleteMany` fails when audit rows reference the tenant; tests leak tenants. Documented as environmental, not a flake. The constraint is correct (SOC 2 CC7.2); the test pattern was wrong. Lesson institutionalized in CLAUDE.md.
- **Test cold-start flake on Neon** — first test run after idle sometimes fails on Prisma cold-start; retry succeeds. Documented as environmental, not a flake. Don't disable; don't retry-loop; just be aware.
- **22-PR arc composed via stacked branches + `-X ours` merge** — `blackline-arc-recons` → `blackline-arc-tasks` → `blackline-arc-flux` → `blackline-arc-capstone`. The capstone branch's three-way merge of all three phase branches had 9 schema collision sites; aborted the complex 3-way merge and re-did with `git merge -X ours`, then manually layered Phase 3 backrefs across Tenant/LegalEntity/Book/Period/Account/User. Backref blocks across all three phases needed to coexist in one schema. Lesson: stacked branches WORK but the final merge is non-trivial; budget time for it.

Tuned for a 5-7 day close window: recon EXCEPTION = high; recon PREPARED ≥2d stale = medium; task BLOCKED + required = high; flux statement NEEDS_COMMENT ≥3d = high. The aging thresholds are the controller's institutional knowledge.

### Close-task state-history decisions (2026-06-10)

- **Append-only DB trigger with `pg_trigger_depth()` cascade carve-out** — same as `audit_log`, but the FK chain `close_task → close_task_state_change` would deadlock with a strict refuse-all-DELETE trigger when a tenant tears down. Solution: trigger checks `pg_trigger_depth()` and lets cascade-context deletes through (depth > 1). Direct DELETE from a client query is always depth = 1 and stays blocked. SOC 2 audit-trail property preserved; right-to-erasure still works.
- **Nullable `changedById` is a deliberate concession to the backfill** — the migration can't invent an actor for historical rows. The alternative — backfilling to a "system user" id — would have been a lie.
- **State-change writes inside `$transaction` with the close-task update** — atomic. A failed insert rolls the status update back too. The audit_log call stays outside the transaction (matches the existing pattern across the codebase; audit is best-effort).
- **`recurringBlockers` semantics changed from current-snapshot to ever-blocked** — the return shape stayed identical so the UI didn't need touching, but the meaning changed. Documented in the docstring + commit message. The fixture update on the pre-existing test was unavoidable — the test was implicitly relying on snapshot semantics; under the new contract it had to mint the matching state-change row by hand because it created the task via raw Prisma, bypassing the action layer.
- **`createMany` for INITIAL rows on bulk instantiation** — one round trip for N tasks instead of N transactions. Append-only trigger allows bulk INSERT (only UPDATE/DELETE blocked), so this is clean.
- **`reason` populated only for BLOCKED + WAIVED** — start/complete/unblock leave it null. Reduces noise; captures the audit-relevant signal. The block reason is the most-asked-about field when reviewing close history.
